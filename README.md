# Demucs Web

YouTube 음원을 받아 Demucs(htdemucs)로 스템 분리하고 BPM을 뽑는 웹 서비스.
Windows에서 직접 돌리기 어려운 조합(Blackwell GPU + CUDA + demucs)을 Docker 리눅스 컨테이너로 해결한다.

검증 환경: Windows 11 Pro 26200 / RTX 5060 Ti 8GB (드라이버 595.79) / Ryzen 7 7800X3D / RAM 16GB
WSL2 2.7.11 · Docker Desktop 29.6.2 · Compose v5.3.1

측정: 5분 36초 곡 → **37초** (다운로드·분리·BPM·인코딩 전부 포함)

---

## 요구 사항

- **NVIDIA GPU + Docker** (GPU 없이 CPU 로도 돌지만 5분 곡에 수 분 걸린다)
- Windows 라면 WSL2 백엔드의 Docker Desktop. 리눅스면 nvidia-container-toolkit
- 디스크 여유 15GB 이상 (이미지 ~9GB + 결과물)

GPU 가 Blackwell(sm_120)이 아니면 `Dockerfile` 의 베이스 이미지 태그를 맞는 CUDA 버전으로
바꿔야 할 수 있다. 아래 "BPM 검출" 위쪽의 표 참고.

## 빠른 시작

```bash
git clone https://github.com/jw-heo97/demucs_web.git
cd demucs_web
cp .env.example .env          # Windows: copy .env.example .env
docker compose up -d --build
```

브라우저에서 <http://127.0.0.1:8080>

첫 기동 때 관리자 계정이 만들어진다. `.env` 의 `ADMIN_PASSWORD` 를 비워두면
임의 비밀번호를 만들어 로그에 **한 번만** 찍는다:

```bash
docker compose logs api | grep 비밀번호
```

> ⚠️ 이 저장소에는 계정·토큰·접속기록·분리 결과물이 들어 있지 않다 (`data/` 는 `.gitignore`).
> 클론한 뒤 처음 띄우면 계정이 새로 생성된다.

페이지 구성:

- **분리 작업** — 주소 입력, **저장 제목 지정**, 포맷/대상 선택, 보관함
- **송 맵** — 구간(시작 시각 · 이름 · BPM · 박자표)을 들으면서 직접 잡는다
- **YouTube 검색** — 검색 → 미리보기 → `선택` 을 누르면 주소와 제목이 1번 탭에 자동으로 채워진다
- **보안** — 우측 상단 버튼(다이얼로그). 토큰 관리 · 비밀번호 변경 · 접속 기록

## 송 맵

**곡 구성표가 박자 · 마디 · 메트로놈 · 예비박의 단일 원천이다.**

자동 검출을 아무리 다듬어도 완벽해지지 않는다 (아래 "BPM 검출" 참고). 그래서 검출은
**출발점**으로만 쓰고 사용자가 직접 잡는 쪽으로 설계했다.

### 시간이 아니라 마디로 센다

시간(초)으로 구간을 잡으면 중간에 3/4 마디가 하나 끼는 순간 **뒤쪽이 전부 밀린다.**
마디 기반은 앞 마디 길이를 순서대로 쌓으므로 그런 문제가 없다. 그래서 기준 시각은
**1마디 1박 하나뿐**이고 나머지는 전부 마디 번호로 지정한다.

```
기준     1마디 1박 = 0:00.331,  기본 ♩ = 150

마디      이름      박자   적용 범위
  1     Intro      4/4    1~8마디
  9     Verse      4/4    9~30마디
 31     Bridge     3/4    31~33마디
 34                4/4    34마디
 35                3/4    35~37마디
 38     Chorus     4/4    38마디~끝
```

**한 표에서 이름과 박자를 같이 다룬다.** 각 항목이 "이 마디부터" 하나를 뜻하므로,
이름만 붙여도 되고(박자는 앞에서 물려받음) 박자만 바꿔도 된다(위 34·35마디).
이름은 다음 이름이 나올 때까지 이어진다 — 위에서 Bridge 는 31~37마디 내내 표시된다.

실측 (위 구성 그대로 저장한 결과):

| 마디 | 박자 | 시작 | 길이 |
|---|---|---|---|
| 30 | 4/4 | 46.731s | 1.600s |
| 31 | **3/4** | 48.331s | 1.200s |
| 33 | 3/4 | 50.731s | 1.200s |
| 34 | **4/4** | 51.931s | 1.600s |
| 35 | **3/4** | 53.531s | 1.200s |
| 38 | **4/4** | 57.131s | 1.600s |

3/4 마디 3개가 낀 뒤에도 34마디 시작 시각이 기대값과 **0.00 ms** 차이다.

### 편집

| 항목 | 설명 |
|---|---|
| **기준** | `현재 위치` 로 1마디 1박을 찍고 `±10ms` 로 미세 조정. 기본 BPM 은 직접 입력하거나 `탭` 으로 두드려 잡는다 |
| **마디** | 아래쪽에 마디 번호를 입력하고 `추가`. **번호 순서대로 자동 정렬**되므로 30마디를 나중에 넣어도 9마디와 31마디 사이로 들어간다 |
| 행 버튼 | `▶` 그 마디로 이동 · `현재` 재생 위치의 마디로 옮기기 · `삭제` |

표는 언제나 마디 번호 순이다. 행의 마디 번호를 고치면 **입력을 마친 시점에** 정렬되고
(한 글자 칠 때마다 순서가 바뀌면 못 쓴다) 포커스는 그 행에 그대로 남는다.
이미 있는 마디 번호를 넣으면 되돌리고 알려준다.

1마디 항목은 지울 수 없다 (기준점이라서). 마디 번호도 위쪽 `1마디 1박` 으로만 바꾼다.

재생 중에는 **`34마디 · 2박`** 처럼 마디와 박 번호가 실시간으로 표시되고,
다음 이름이 몇 초 뒤인지도 함께 나온다 (악보 세듯 따라갈 수 있게).

### 클릭할 박 고르기

마디 행의 박 번호 토글로 **그 구간에서 소리 낼 박**을 고른다. 4/4 에서 `1` 만 켜면
마디 첫 박만 울리고, `1`·`3` 만 켜면 두 번씩 울린다. 전부 켜면 특별 설정 없음으로 저장된다.

실측 (17마디부터 1박만, 25마디부터 1·3박):

```
 1~16마디 (전부)     박자 64개 중 소리 64개   (16마디 × 4)  ✓
17~24마디 (1박만)    박자 32개 중 소리  8개   ( 8마디 × 1)  ✓
25~32마디 (1·3박)    박자 32개 중 소리 16개   ( 8마디 × 2)  ✓
```

### 마디 일괄 입력

`1/17/30/100/102/103` 처럼 붙여 넣고 `한번에 추가` 를 누르면 그 마디들이 한 번에 생긴다.
`/`, `,`, 공백 아무거나 구분자로 쓸 수 있고, 이미 있는 마디는 건너뛰고 알려준다.
박자는 각 마디에 그때 적용 중이던 값을 물려받는다.

### 버전 (탭)

`연습용 / 원곡용` 처럼 구성표를 **여러 벌** 두고 탭으로 오갈 수 있다.
버전마다 메트로놈 파일이 따로 구워진다:

```
라일락_click.wav          ← 활성 버전 (믹서가 집는 파일)
라일락_click_기본.wav      ← 버전별 파일
라일락_click_연습용.wav
```

버전을 지우면 그 파일도 함께 지워진다. 이름을 바꾸면 파일 이름도 따라간다.

> 버전마다 wav+mp3 가 생기므로 5분 곡 기준 버전당 60MB 정도 늘어난다.
> `.env` 에서 `WAV_SUBTYPE` 이나 분리 시 포맷을 mp3 로만 두면 크게 줄어든다.

### 이력 (자동 백업)

구성표를 저장·전환·재검출할 때마다 **직전 버전이 자동으로 보관된다**
(`_map_history.json`, 최근 20개). 버전 탭 오른쪽 `이력 N` 에서 되돌릴 수 있다.

> 손으로 오래 잡은 작업이 한 번의 덮어쓰기로 날아가는 일을 막기 위한 것이다.
> 실제로 그런 사고가 한 번 있었고, 그때는 복구 수단이 없었다.

### N/8 박자

BPM 은 관례대로 **4분음표(♩) 기준**이다 (DAW 들도 박자표와 무관하게 템포는 ♩=X).
따라서 분모가 8이면 클릭은 8분음표마다 찍힌다.

```
♩=150 · 6/8  →  클릭 간격 200.0 ms (♩ 400ms 의 절반),  한 마디 1200.0 ms
```

분모는 2 · 4 · 8 · 16 을 고를 수 있다.

### 마디 첫 박은 소리가 다르다

| | 주파수 | |
|---|---|---|
| 마디 첫 박 | **1500 Hz** | 길이 55ms |
| 나머지 박 | **1000 Hz** | 길이 45ms |

박자표가 바뀌어도 강세가 따라간다. 실측 (4/4 → 5마디부터 3/4 로 바꾼 파일에서
클릭마다 FFT 로 주파수를 측정):

```
  #   마디   박     시각    강세    측정 주파수
 16    5    1    6.731     ●      1500 Hz     ← 3/4 로 바뀐 첫 마디
 17    5    2    7.131     ·      1000 Hz
 18    5    3    7.531     ·      1000 Hz
 19    6    1    7.931     ●      1500 Hz     ← 3박 뒤에 정확히 강세
```

강세 위치는 `beats_per_bar` 하나로 계산하지 않고 **박자마다 불리언 배열**로 넘긴다.
곡 중간에 박자표가 바뀌면 "N박마다 강세" 규칙 하나로는 표현할 수 없기 때문
(`render_metronome(..., accents=...)`).

### 저장 형식

```json
{"anchor": 0.331, "bpm": 150.0,
 "ranges": [{"from_bar": 1,  "name": "Intro",  "beats_per_bar": 4, "beat_unit": 4, "bpm": null},
            {"from_bar": 31, "name": "Bridge", "beats_per_bar": 3, "beat_unit": 4, "bpm": null}]}
```

- 이름과 박자가 **한 항목**에 들어간다. 이름만 붙이면 박자는 앞에서 물려받고,
  박자만 바꾸면 이름은 앞 이름이 계속 표시된다.
- `bpm` 이 `null` 이면 기본 BPM 을 쓴다. `ranges` 가 비면 곡 전체 4/4 로 본다.
- 박자 배열은 `_meta.json` 에 저장하지 않는다 — 구성표에서 언제든 다시 만들 수 있고,
  곡당 수백~수천 개라 메타 파일만 커지기 때문.

### 보관함

곡이 수십 개로 늘어나도 쓸 수 있게 만들어져 있다.

- **접기/펼치기** — 기본은 한 줄 요약(제목·BPM·길이·파일 수·용량·날짜). 클릭하면 펼쳐진다.
  진행 중인 작업은 항상 펼쳐져 있다.
- **멀티트랙 믹서** — 펼치면 바로 재생할 수 있다. 자세한 내용은 아래.
- **제목 검색** — 목록 상단 입력란으로 즉시 필터링
- **디스크 기반 복원** — 목록이 메모리에만 있으면 컨테이너를 한 번만 재시작해도 통째로 사라지고
  `data/output` 의 폴더들이 UI에서 안 보이는 고아가 된다. 그래서 결과 폴더마다 `_meta.json` 을
  남기고, 기동할 때 `data/output` 을 훑어 목록을 복원한다. `_meta.json` 이 없는 예전 폴더는
  `info.txt` 에서 BPM·길이를 건져낸다.

> `JOB_RETENTION_SEC` 기본값은 **0(자동 삭제 안 함)** 이다. 보관함으로 쓰는 이상 자동 삭제는
> 위험하기 때문. 굳이 필요하면 양수로 바꿀 수 있다.

### 멀티트랙 믹서

보관함에서 곡을 펼치면 스템을 **동시에** 재생하는 믹서가 뜬다. 스템 분리는 결국
같이 들어보면서 확인하는 작업이라 단순 재생 대신 이렇게 만들었다.

- 재생/일시정지, 탐색(seek) — 모든 트랙이 함께 움직인다
- 트랙별 **볼륨 · 음소거 · 솔로** — 보컬을 음소거하면 그 자리에서 MR이 된다
- **메트로놈** 트랙도 함께 뜬다 (아래 참고)
- **예비박** 2·4·8박 — 재생을 누르면 클릭이 먼저 울리고 시작한다
- **들리는 트랙만 믹스 다운로드** — 지금 들리는 조합 그대로 한 파일로 받는다

### 예비박 (count-in)

파일에 굽지 않고 **브라우저에서 Web Audio 로 만든다.** 파일에 넣으려면 모든 스템 앞에
같은 길이의 무음을 붙여 전부 재인코딩해야 하고, 그러면 곡 중간부터 연습할 때는 쓸 수 없다.
템포는 그 곡의 BPM 을 쓰고, 첫 박은 높은 음으로 구분한다. 카운트다운은 재생 버튼에 숫자로 표시된다.

**언제 붙는가**

- 플레이어: **곡 처음부터 재생할 때만** (0.25초 이내). 중간에서 일시정지했다 다시 누를 때마다
  붙으면 오히려 방해가 되기 때문.
- **믹스 다운로드 파일: 맨 앞에 한 번 박혀서 저장된다.** 이건 브라우저가 아니라 서버가 만든다 —
  곡 앞에 무음을 덧대고 그 구간에 클릭을 찍되, 마지막 클릭이 곡의 첫 박보다 정확히 한 박
  앞에 오도록 앞머리 길이를 역산한다.

실측 (믹스 파일에서 클릭 위치를 직접 찾아 확인):

| 곡 | 한 박 | 클릭 간격 | 마지막 클릭 → 곡의 첫 박 |
|---|---|---|---|
| 라일락 | 400.5 ms | 400.5 / 400.5 / 400.5 | **400.6 ms** ✓ |
| 라시사 | 362.8 ms | 362.8 / 362.8 / 362.8 | **363.0 ms** ✓ |

#### 곡의 박자 격자에 맞춘다 — 이게 없으면 진입이 어긋난다

단순히 "지금부터 4박 세고 재생" 으로 만들면 **곡의 첫 박과 어긋난다.**
클릭 간격은 일정한데 음악 진입만 최대 한 박까지 밀리기 때문에 예비박이 곡에 안 붙는 것처럼 들린다.

실측 (수정 전, 위치 0 에서 재생):

| 곡 | 한 박 | 곡의 첫 박 위치 | 마지막 클릭 → 첫 박 |
|---|---|---|---|
| 라일락 | 400 ms | 0.354 s | **752 ms (1.88박)** |
| 라시사 | 364 ms | 0.104 s | **468 ms (1.29박)** |

그래서 재생 위치 이후 **곡의 다음 박자** `b` 를 찾고, 마지막 클릭이 `b` 보다 정확히 한 박
앞에 오도록 역산해서 오디오 시작 시각을 정한다. 수정 후에는 두 곡 다 오차 없이 한 박(400.0 ms /
363.6 ms)이 나온다.

- 박자 위치는 `GET /api/jobs/{id}/beats` 로 믹서를 열 때만 받아온다
  (곡당 수백 개라 작업 목록에 실으면 1초 폴링이 무거워진다)
- **격자가 없는 구간은 되짚는다.** 박자는 드럼 스템에서 뽑기 때문에 드럼이 늦게
  들어오는 곡은 앞부분에 박자가 없다 (라일락은 첫 박이 13.148초). 그대로 쓰면
  "다음 박자" 가 13초 뒤로 잡혀 음악 시작 시각이 음수가 되고, 0 으로 잘리면서
  음악이 즉시 시작돼 **29박이나 어긋난다.** 그래서 `b -= floor((b-pos)/step)*step`
  으로 격자를 되짚는다 (서버 `_prepend_count_in` 의 `first % step` 과 같은 처리)
- `<audio preload="auto">` 로 미리 버퍼링한다. `metadata` 로 두면 `play()` 시점에
  버퍼링이 시작돼 진입이 밀린다
- `setTimeout` 이 늦게 깨어난 만큼은 재생 위치를 앞당겨 보정한다

### 들리는 트랙만 믹스 다운로드

믹서에서 솔로/음소거로 조합을 만든 뒤 버튼을 누르면 그 조합만 합친 파일이 만들어진다.
볼륨 슬라이더 값도 그대로 반영된다. 결과는 `data/output/<곡>/mix/` 에 쌓이고
같은 조합이면 덮어쓴다.

합성을 서버에서 하는 이유는 두 가지다 — 브라우저에는 mp3 인코더가 없고,
서버는 **wav 원본**으로 합칠 수 있어 재인코딩 손실이 쌓이지 않는다.
합친 결과가 0dB 를 넘으면 잘라내지 않고 전체 레벨을 낮춘다(왜곡 방지).
- mp3 가 있으면 mp3 를 쓴다 (wav 보다 4배 작아 스트리밍이 빠르다)
- 믹서는 한 번에 하나만 살아 있다. 다른 곡을 펼치면 이전 것은 해제된다

구현 메모:

- 스템 수만큼 `<audio>` 를 만들고 첫 트랙을 마스터 시계로 삼는다. 매 프레임 확인해서
  마스터에서 **0.15초 이상** 벌어진 트랙만 맞춘다 (매번 맞추면 오히려 소리가 튄다).
- 탐색이 되려면 서버가 Range 요청에 `206` 을 줘야 한다. Starlette 의 `FileResponse` 가
  처리해 준다 — 실측으로 `Content-Range: bytes 0-1023/11664240` 확인.
- 파일은 기본 `inline` 으로 서빙해 `<audio>` 가 바로 재생하고, 다운로드 링크만
  `?download=1` 로 `attachment` 를 받는다.
- 목록은 1초마다 갱신되는데, **전체를 다시 그리면 재생 중인 믹서가 죽는다.**
  그래서 작업 구성이 바뀔 때만 전체 렌더(`paint`)하고, 진행률만 바뀐 경우엔
  해당 요소만 고쳐 쓴다(`patch`).

### 메트로놈과 BPM

분리할 때 **메트로놈 트랙**(`_click.wav` / `_click.mp3`)을 함께 만든다. 고정 그리드가 아니라
**검출된 실제 박자 위치**에 클릭을 찍으므로 연주의 미세한 밀당을 따라간다.
마디 첫 박은 1500Hz, 나머지는 1000Hz 로 구분한다 (기본 4/4, `BEATS_PER_BAR` 로 변경).
믹서에 별도 트랙으로 뜨니 볼륨을 따로 조절하거나 끌 수 있다.

#### ⚠ librosa 의 2배/절반 오류를 보정한다

librosa 의 `beat_track` 은 템포 사전확률이 120 BPM 근처에 강하게 걸려 있어서
빠른 곡을 **정확히 절반으로** 접는 일이 잦다. 실측:

| 곡 | 실제 | 보정 전 | 보정 후 |
|---|---|---|---|
| 라일락 (Mrs. Green Apple) | 150 | **74.9** | 152.0 |
| 나다움 (Official髭男dism) | 165 | **82.03** | 166.71 |

보정 방식은 "범위를 벗어나면 무조건 2배" 가 **아니다.** 그렇게 하면 진짜 느린 발라드를
망가뜨린다. 대신 자기상관 템포그램에서 T 와 2T 의 **근거 강도를 비교해서**,
2T 쪽이 원래 값의 80% 이상 지지를 받을 때만 옮긴다
(위 두 곡의 근거비는 0.95 / 0.91 로 충분히 강했다).

#### hop_length 는 256 을 쓴다

librosa 의 박자 시각은 hop 단위로 양자화된다. 기본값 512(=11.6ms)면 템포 추정이
프레임 수로 반올림돼 눈에 띄게 틀어진다. 256(=5.8ms)으로 낮추면 크게 좋아진다.

| 곡 | 실제 | hop 512 | **hop 256** | hop 128 |
|---|---|---|---|---|
| 라일락 | 150 | 152.00 | **149.80** | 149.80 |
| 라시사 | 165 | 166.71 | **165.38** | 165.37 |
| 5분 곡 분석 시간 | — | 4~19초 | **9~11초** | 165~241초 |

128 이 조금 더 정확하지만 분석에 3~4분이 걸려 실용적이지 않다.

보고 값은 템포그램 추정치를 그대로 쓴다. 박자 간격 **중앙값으로 덮어쓰면 오히려 나빠진다**
(실측: 라시사 165.38 → 164.06). 추적이 전혀 다른 템포에 물린 경우(10% 이상 차이)에만
중앙값을 신뢰한다.

#### 그래도 0.2~0.4 BPM 은 틀린다 → 직접 고칠 수 있다

보관함에서 곡을 펼치면 BPM 입력란과 `÷2` `×2` `적용` `자동 재검출` 버튼이 있다.
직접 값을 넣으면 그 템포의 **균일 그리드**로 메트로놈을 다시 만든다.
이때 첫 박 위치는 검출된 실제 첫 박자에 맞추므로 곡과 어긋나지 않는다.

이미 분리해 둔 곡에도 쓸 수 있다 — 저장된 드럼 스템을 다시 읽어 처리하므로
재분리가 필요 없다. (`drums` 스템이 있어야 하니 분리 대상이 `all` 이거나 `drums` 여야 한다)

입력한 제목이 **출력 폴더 이름이자 파일 접두사**가 된다. 비워두면 YouTube 제목을 그대로 쓴다.

## 인증 · 권한

모든 경로가 로그인으로 보호된다. 공개 경로는 `/healthz`(Docker 헬스체크)와
로그인 화면 자산뿐이다.

역할은 `admin` 과 `user` 두 가지다.

| | user | admin |
|---|---|---|
| 분리 · 보관함 · 송 맵 · 검색 | ✅ | ✅ |
| **보안 화면** (계정 관리 · 전체 접속 기록) | ❌ | ✅ |

**보안 화면은 관리자에게만 보인다.** 버튼을 숨기는 데서 그치지 않고
`/api/auth/users`, `/api/auth/log` 를 서버에서 `403` 으로 막는다 — 숨기기만 하면
API 를 직접 부르면 그만이기 때문.

자기 비밀번호 변경과 자기 기기 토큰 관리는 역할과 무관하게 본인 것만 다룰 수 있다.

계정은 보안 화면에서 추가·삭제하고 역할을 바꾼다. **마지막 관리자는 삭제하거나
강등할 수 없다** — 자기 자신을 잠가버리는 상황을 막기 위한 것.

앱 전체를 특정 역할로 제한하고 싶으면 `.env` 의 `REQUIRE_ROLE` 을 채운다
(예: `admin`). 기본은 비어 있어 로그인한 사용자면 누구나 쓸 수 있다.

### 첫 로그인

`.env` 의 `ADMIN_PASSWORD` 를 비워두면 첫 기동 때 임의 비밀번호를 만들어 로그에 한 번만 찍는다.

```powershell
docker compose logs api | Select-String "비밀번호"
```

로그인 후 **보안 탭에서 반드시 변경**할 것. 비밀번호를 바꾸면 다른 기기의 세션이 전부 해제된다.

계정·토큰·접속기록은 `data/auth/` 에 남아 컨테이너를 지워도 유지된다.
비밀번호를 잊으면 `data/auth/users.json` 을 지우고 재시작하면 새 관리자가 만들어진다.

### 토큰

- 로그인하면 기기마다 세션 토큰이 하나씩 발급된다 (기본 30일). 쿠키는 `HttpOnly` 라
  JS 로 읽을 수 없어 XSS 로 토큰이 새지 않는다.
- 보안 탭에서 발급된 토큰을 **기기별로 확인·해제**할 수 있다. 잃어버린 기기는 여기서 끊는다.
- 스크립트용 **API 토큰**도 발급할 수 있다. `Authorization: Bearer <토큰>` 으로 쓴다.
  원문은 발급 직후 한 번만 표시되고, 서버에는 SHA-256 만 저장된다.
- 비밀번호는 `hashlib.scrypt` 로 해싱한다(의존성 추가 없이 표준 라이브러리).
  로그인 5회 실패하면 해당 계정이 5분간 잠긴다.

> scrypt 주의: OpenSSL 의 기본 메모리 상한이 32MB 라서 `n=2^15, r=8` 이면 정확히 걸린다.
> `maxmem` 을 명시하지 않으면 `memory limit exceeded` 로 죽는다 (실제로 겪음).

## 접속 IP 기록

접속 기록은 `data/auth/access.jsonl` 에 JSON Lines 로 쌓이고 보안 탭에서 볼 수 있다.
로그인 성공/실패/잠금, 로그아웃, 토큰 발급·해제, 비밀번호 변경, 그리고 상태를 바꾸거나
파일을 가져가는 요청을 남긴다. (1초마다 도는 폴링까지 남기면 로그가 쓸모없어지므로 제외)

### 현재 구성: Tailscale (해결됨)

```
폰·노트북 ──HTTPS──▶ <기기이름>.<tailnet>.ts.net ──▶ tailscale serve (Windows)
                                                      │ X-Forwarded-For
                                                      ▼
                                            127.0.0.1:8080 ──▶ 컨테이너
```

`tailscale serve` 가 Windows 호스트에서 프록시하면서 실제 주소를 `X-Forwarded-For` 로
넘겨주므로 **기기별 IP 가 정확히 기록된다.** `.env` 는 다음과 같다:

```ini
WEB_BIND=127.0.0.1        # LAN 개방 없음 — Tailscale 경유만
TRUST_PROXY_HEADER=1
```

실측 기록:

| 기록된 IP | 기기 |
|---|---|
| `100.120.104.86` | 아이폰 (tailnet) |
| `100.123.151.112` | 이 PC (tailnet) |
| `172.18.0.1` | 호스트에서 `127.0.0.1:8080` 직접 접속 (프록시 미경유) |

이 구성으로 세 가지가 한꺼번에 해결됐다 — **기기별 접근 제어 · HTTPS · 실제 IP 기록.**

> `tailscale serve` 는 공유 비밀 헤더를 붙이는 기능이 없어서 `PROXY_SECRET` 은 비워둔다.
> 포트가 `127.0.0.1` 로만 열려 있어 외부에서 헤더를 위조할 수는 없지만,
> **이 PC 안의 다른 프로그램**은 위조할 수 있다. 가정용으로는 충분한 수준.

### ⚠ 참고: Docker 단독으로는 왜 안 되는가

**Docker Desktop for Windows 는 출발지 IP 를 보존하지 않는다.** 실측 결과:

| 접속 출발지 | 컨테이너가 본 IP |
|---|---|
| 같은 PC (`127.0.0.1`) | `172.17.0.1` |
| 같은 PC의 LAN IP | `172.17.0.1` |
| **WSL(별도 네트워크 네임스페이스)에서 LAN IP로** | `172.18.0.1` |

포트를 실제로 여는 것은 Windows 프로세스(`com.docker.backend.exe`, `wslrelay.exe`)이고
컨테이너까지 NAT 를 거치므로, **원격 접속이어도 전부 브리지 게이트웨이로 보인다.**
즉 기본 상태에서 IP 칸은 의미가 없다. UI 상단에도 이 경고가 뜬다.

**사용자·기기(토큰)·시각 기록은 정확하다.** 어차피 LAN 은 DHCP 로 IP 가 바뀌므로,
"누가 어느 기기로" 는 토큰 쪽이 더 확실한 단서다.

### 진짜 IP 를 남기려면

Windows 호스트에 리버스 프록시를 둬서 프록시가 실제 IP 를 보고 `X-Forwarded-For` 로 넘긴다.

1. Docker 는 루프백에만 열어둔다 — `.env` 에 `WEB_BIND=127.0.0.1`, `WEB_PORT=8081`
2. Windows 용 Caddy 를 받아 아래 `Caddyfile` 로 실행한다 (`caddy run`)

   ```caddyfile
   :8080 {
       reverse_proxy 127.0.0.1:8081 {
           header_up X-Forwarded-For {remote_host}
           header_up X-Proxy-Secret  "여기에-긴-임의-문자열"
       }
   }
   ```
3. `.env` 에 `TRUST_PROXY_HEADER=1` 과 같은 `PROXY_SECRET` 을 넣고 재기동

`PROXY_SECRET` 이 설정되면 그 헤더가 일치할 때만 `X-Forwarded-For` 를 믿으므로
클라이언트가 헤더를 위조해도 통하지 않는다.

> **uvicorn 주의:** uvicorn 은 `proxy_headers` 가 **기본 True** 라서 그냥 두면
> `X-Forwarded-For` 로 `request.client.host` 를 덮어쓴다. 그러면 아무나 헤더를 넣어
> 기록될 IP 를 속일 수 있다(실제로 재현됨). 그래서 Dockerfile 에서 `--no-proxy-headers`
> 로 끄고, 신뢰 판단은 `auth.client_ip()` 한 곳에서만 한다.

## 접근 제어 (네트워크 계층)

**현재는 Tailscale 경유만 열려 있다.** `WEB_BIND=127.0.0.1` 이라 LAN 에서 직접 접속할 수 없고
(실측 확인), 외부 노출은 `tailscale serve` 가 담당한다 → 위 "접속 IP 기록" 참고.

```powershell
tailscale serve --bg 8080      # https://<기기>.<tailnet>.ts.net 로 노출
tailscale serve status
```

폰·노트북에 Tailscale 앱을 깔고 같은 계정으로 로그인하면 그 주소로 접속된다.
공유기 포트포워딩도, 공인 IP 도 필요 없다.

### 🔴 포트포워딩으로 인터넷에 직접 여는 것은 권하지 않는다

`WEB_BIND=0.0.0.0` + 공유기 포트포워딩 조합은 다음 문제를 안는다:

1. **HTTP 라서 비밀번호가 평문으로 전송된다.** 인터넷 경로에서는 중간의 누구나
   아이디·비밀번호와 세션 쿠키를 볼 수 있고, 쿠키를 훔치면 비밀번호 없이도 로그인된다.
2. 공인 IP 에 열린 포트는 며칠 안에 자동 스캐너에 발견된다. 로그인 잠금(5회/5분)이
   무차별 대입을 늦추긴 하지만, 사전 단어 조합 비밀번호는 오래 못 버틴다.
3. GPU 작업 큐라 계정이 뚫리면 남의 작업에 GPU 를 갈아넣게 된다.

Tailscale 은 이 셋을 모두 피한다. 굳이 직접 노출해야 한다면 최소한 긴 임의 비밀번호와
HTTPS(도메인이 있으면 Caddy 가 Let's Encrypt 인증서를 자동 발급) 는 갖출 것.

### 왜 컨테이너 안에서는 IP 화이트리스트가 불가능한가

실측 결과, Docker Desktop for Windows는 **원본 클라이언트 IP를 보존하지 않는다.**
원격 접속(WSL → LAN IP)까지 확인했는데 결과는 같았다. 자세한 표는 위 "접속 IP 기록" 참고.

```
127.0.0.1 에서 접속       → 컨테이너가 본 peer = 172.17.0.1
192.168.0.10 에서 접속 → 컨테이너가 본 peer = 172.17.0.1
WSL 에서 LAN IP 로 접속    → 컨테이너가 본 peer = 172.18.0.1
```

포트를 실제로 여는 것은 Windows 프로세스(`com.docker.backend.exe`, `wslrelay.exe`)이고,
컨테이너로는 NAT를 거쳐 게이트웨이 주소로 도착한다. 따라서 Caddy/nginx의 `remote_ip` 매처를
컨테이너 안에서 써봐야 **모든 클라이언트가 동일하게 보여 필터링이 무의미하다.**
(`X-Forwarded-For` 를 믿는 `client_ip` 매처는 클라이언트가 헤더를 위조할 수 있어 더 나쁘다.)

### 그래서 선택지

| 방법 | 강도 | 설명 |
|---|---|---|
| **Windows 방화벽 인바운드 규칙** | 중 | 포트 8080에 대해 원격 IP를 제한. Docker보다 앞단(Windows 계층)에서 걸리므로 실제로 동작한다. 관리자 권한 필요 |
| **Tailscale / WireGuard** (권장) | 높음 | `WEB_BIND=127.0.0.1` 유지하고 VPN으로만 접근. 기기별 키라서 IP보다 안전하고 외부에서도 쓸 수 있다 |
| **mTLS 클라이언트 인증서** | 높음 | 인증서 없는 기기는 TLS 핸드셰이크 자체가 실패 |

> **MAC 주소 필터링은 불가능하다.** MAC은 같은 L2 세그먼트에서만 보이고 라우터를 하나만
> 넘어가도 사라진다. 게다가 위조가 매우 쉽다. "특정 기기만" 이 목표라면 위 2·3번이 맞는 답이다.
> 공유기에서 MAC→고정 IP를 예약한 뒤 그 IP를 방화벽에 넣는 방식이 "MAC 화이트리스트"의
> 현실적인 대체재다.

`Caddyfile` 은 나중에 리버스 프록시가 필요할 때를 위해 남겨뒀지만 현재 compose에는 연결되어 있지 않다.

## 구조

프론트엔드는 **React + TypeScript (Vite)** 다. 나중에 앱(Capacitor/Tauri)으로 감쌀 수 있도록
API 를 오리진과 분리해 뒀다.

```
demucs-web/
├─ web/                     React 앱 (빌드 결과만 이미지에 들어간다)
│  ├─ src/
│  │  ├─ api.ts             fetch 래퍼 — 쿠키·Bearer 토큰 둘 다 지원
│  │  ├─ types.ts
│  │  ├─ lib/songmap.ts     마디 계산 (서버 beats_from_map 과 같은 규칙)
│  │  ├─ hooks/useAudioEngine.ts   여러 스템 동시 재생 + 드리프트 보정
│  │  └─ components/
│  │     ├─ Waveform.tsx    파형 편집기 (이 앱 조작의 중심)
│  │     ├─ Mixer.tsx       트랜스포트 · 트랙 · 예비박
│  │     ├─ SongMapTab.tsx  구성표 편집
│  │     ├─ WorkTab.tsx     분리 작업 + 보관함
│  │     ├─ SearchTab.tsx   YouTube 검색
│  │     └─ SecurityDialog.tsx
│  └─ vite.config.ts        base:"./" — 앱에서 file:// 로 열려도 자산을 찾는다
```

### 앱으로 만들 때

- `base: "./"` 로 빌드하므로 `web/dist` 를 그대로 Capacitor/Tauri 에 넣으면 된다.
- 앱은 쿠키를 못 쓰는 경우가 있어 **로그인 응답에 토큰 원문**이 함께 온다.
  `api.ts` 가 `localStorage` 에 저장해 `Authorization: Bearer` 로 보낸다 (실측 확인).
- 서버 주소가 다르면 `VITE_API_BASE` 로 지정하고, `.env` 의 `CORS_ORIGINS` 에 앱 오리진을 넣는다.

### 개발

```powershell
cd web
npm install
npm run dev        # http://localhost:5173 — /api 는 컨테이너(8080)로 프록시된다
```

```
demucs-web/
├─ Dockerfile              cu128 베이스 + ffmpeg + 모델 사전 다운로드
├─ docker-compose.yml      GPU 예약, 볼륨, 포트 바인딩
├─ .env.example            설정 (복사해서 .env 로)
├─ Caddyfile               (미사용 — 위 "접근 제어" 참고)

├─ data/output/            결과물 (Windows에서 바로 열림)
└─ app/
   ├─ config.py            환경변수 설정

   ├─ separator.py         모델 상주 + 분리 + BPM

```

API 는 `401`, 웹 페이지는 로그인으로 `303` 리다이렉트한다.

`format`: `wav` \| `mp3` \| `both` · `target`: `all` \| `vocals` \| `drums` \| `bass` \| `other`
`title` 은 선택 — 지정하면 출력 폴더 이름이 된다.

### 검색이 API 키 없이 되는 이유

yt-dlp 의 `ytsearch{N}:질의` 를 `extract_flat` 으로 호출한다. 개별 영상 페이지를 열지 않아
12개 결과에 1초 내외다. 같은 검색어는 5분간 캐싱해 YouTube 를 반복해서 두드리지 않는다.

> **왜 YouTube 화면을 그대로 가져오지 않았나:** YouTube 메인 사이트는 `X-Frame-Options` 로
> iframe 삽입을 거부하고, 설령 띄워져도 동일 출처 정책 때문에 사용자가 그 안에서 무엇을
> 클릭했는지 우리 페이지가 읽을 수 없다. 임베드 플레이어는 단일 영상 재생 전용이라 검색 UI가 없다.
> 그래서 검색 UI를 직접 만들고, 임베드 플레이어는 미리보기 용도로만 쓴다.

### 미리보기가 안 될 때

raw iframe 대신 **IFrame Player API** 를 써서 실패 원인을 코드로 받아 안내한다
(`101`/`150` = 소유자가 임베드 차단, `100` = 비공개/삭제).
`youtube-nocookie.com` 은 광고 차단 확장이 종종 막기 때문에 표준 도메인을 쓴다.

**미리보기가 막혀도 다운로드·분리는 정상 동작한다.** 임베드 차단은 브라우저 재생만 막는 설정이다.

`format`: `wav` \| `mp3` \| `both` · `target`: `all` \| `vocals` \| `drums` \| `bass` \| `other`

`target=all` 이면 4스템을 저장한다. **`_no_보컬` 같은 "제외 믹스" 는 기본으로 굽지 않는다** —
나머지 스템의 합일 뿐이라 믹서에서 음소거로 바로 들을 수 있고, 파일이 필요하면
믹스다운으로 그때 만들면 된다. 전체 모드에서 파일 수와 용량이 그만큼 줄어든다
(9종 → 5종, 약 44% 감소). 굳이 굽고 싶으면 `minus_mixes: true`.

## 알려진 한계 / 손볼 것

### 구간 안에서는 템포가 일정하다

구성표의 각 구간은 `start + k × (60/bpm)` 로 박자를 만든다. 즉 **구간 안에서는 완전히 균일**하다.
실제 곡이 미묘하게 다르면 구간이 길수록 뒤로 갈수록 밀린다. 실측(한 구간짜리 균일 격자 기준):

| 곡 | 지정 BPM | 곡 후반 25% 에서 추적 박자와의 어긋남 |
|---|---|---|
| 라일락 | 150 | 평균 **194.8 ms** / 최대 199.9 ms (한 박 400ms → 거의 반 박) |
| 라시사 | 165 | 평균 17.7 ms / 최대 47.0 ms |

**당장의 대응은 구간을 쪼개는 것이다.** 밀리기 시작하는 지점에 구간을 하나 더 넣고
`현재` 로 시작점을 다시 잡으면 그 지점부터 위상이 재정렬된다.

더 손본다면:

- 파형을 그려 박자선을 눈으로 맞추게 한다 (피크는 서버가 미리 뽑아둬야 한다 —
  50MB wav 를 브라우저에서 `decodeAudioData` 하면 멈춘다)
- 리타르단도나 라이브 녹음처럼 연속적으로 변하는 템포는 결국 박자 배열 자체를 편집해야 한다
- A-B 구간 반복 (연습 용도로는 이게 체감이 가장 클 것)

관련 코드: [separator.py](app/separator.py) 의 `beats_from_sections()`,
[jobs.py](app/jobs.py) 의 `apply_map()`

### 그 밖에

- 박자 검출은 **드럼 스템** 기준이라 드럼이 늦게 들어오는 곡은 앞부분에 박자가 없다
  (라일락은 첫 박이 13.1초). 예비박을 붙일 때는 격자를 곡 시작 쪽으로 되짚어 쓴다
  (`first % step`) — 인트로의 템포가 본편과 같다는 가정이다.
- 접속 IP 는 리버스 프록시를 두기 전까지 의미가 없다 (위 "접속 IP 기록" 참고)

## 운영 메모

**yt-dlp가 봇 확인에 걸릴 때** → `secrets/README.md` 참고. 집 회선(가정용 IP)이라
데이터센터보다 차단 확률이 훨씬 낮지만, 걸리면 쿠키가 필요하다.

**yt-dlp 갱신** (YouTube 변경으로 다운로드가 깨지면)
```powershell
docker compose build --build-arg YTDLP_VERSION=2026.8.1 api
docker compose up -d
```

**VRAM 부족(OOM)** → `.env` 에 `SEGMENT=5` 정도를 넣고 재기동.

**품질을 더 올리고 싶으면** → `.env` 의 `SHIFTS=2` 이상. 시간이 배수로 늘어난다.

**WSL 메모리 조정** → `%USERPROFILE%\.wslconfig` 의 `memory=8GB`. 수정 후 `wsl --shutdown` 필요.
